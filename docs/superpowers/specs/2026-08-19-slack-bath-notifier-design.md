# 風呂の 5 分前通知 Slack bot 設計

## 目的

予約した風呂の枠が始まる 5 分前に、Slack の共有チャンネルで本人をメンションする。
入り忘れと、次の人を待たせる事故を減らす。

## 範囲

やること。

- 風呂の枠の開始 5 分前に、予約した本人をメンションして 1 回だけ投稿する。

やらないこと。いずれも後から足せる形にしておくが、今は書かない。

- ごはんの投票締切の通知
- 「フォームの受付開始」の告知（アプリに受付開始という概念が無い）
- 予約が成立した瞬間の投稿
- Slack 側からの操作（スラッシュコマンド、ボタン）

## 位置づけ

bot はアプリの外に置き、`/api/v1/` を HTTP で呼ぶ客として振る舞う。Express アプリの中に
組み込まない。

設計した時点では、Pi で動いていたのは Flask 版で、`src/` の Express 版は並走を待っていた。
アプリの中に書くと Pi では動かない。API の契約は両版で同一に保たれていたため、外から呼ぶ
限りどちらが動いていても bot は同じように働き、切替の当日に止める必要が無かった。

Flask 版はその後 3.0.0 で落とした（[express-migration-design](2026-08-19-express-migration-design.md)）。
外に置く判断はそのまま残す。アプリの再起動や入れ替えと bot の生死が切り離されるほうが、
運用中に扱いやすい。

bot は同じホストの `127.0.0.1:8080` を見る。認証は無く、LAN の外には出ない。

## 構成

```
bot/notify.js            本体
bot/slack-users.json     名簿の名前 → Slack member ID（実体は git 管理外）
bot/slack-users.example.json  形だけの見本
bot/sent.json            送信済みの鍵（実行時に自動生成、git 管理外）
bot/kominka-bot.service  systemd ユニット
test/notify.test.js      通知対象を選ぶ純関数のテスト
```

実行時の依存は増やさない。Node 20 の `fetch` だけで足りる。

## 動作

60 秒ごとに次を行う。

1. 今日と明日の `GET /api/v1/bath/<date>` を引く。
2. 返ってきた入れ子（section → room → slot）を平らに並べる。
3. 次の 3 つを全て満たす枠を選ぶ。
   - `state === "taken"`（予約が入っている）
   - `0 < starts_at - now <= 5 分`
   - その枠をまだ送っていない（鍵は後述）
4. 選ばれた枠それぞれについて Slack へ投稿し、送信済みに記録する。

**2 日分を引く理由**。夜の枠は `25:00` まで伸びるが、これは翌 01:00 を指しつつ日付は
入浴を始めた夜のものとして格納される（`src/slots.js` の `stayDate`）。一方、明日の朝
06:00 の枠は明日の日付に属する。今日と明日の 2 日を引けば、5 分先に始まる枠を取り
こぼすことはない。

**`0 <` を条件に入れる理由**。開始時刻を過ぎた枠を送らないため。これが無いと、bot を
夜に起動した瞬間、その日の終わった枠に対して通知が飛ぶ。

**1 分ごとに見に行く理由**。アプリから Slack へ通知を送る仕組みを足していないので、
予約が入ったことを bot が知る手段が無い。こちらから定期的に見に行くしかない。

## 構造

3 つに分ける。

| | |
| --- | --- |
| `due(days, now, sent)` | 通知すべき枠の配列を返す純関数。API の応答・現在時刻・送信済み集合だけを見て、外部に触らない |
| `post(text)` | Webhook へ POST する |
| ループ | 60 秒ごとに fetch → `due` → `post` |

`due` を純関数として切り出すのは、テストを書ける場所をここ 1 つに集めるため。時刻を引数
で受け取る形は `src/slots.js` と `src/meals.js` が既に採っている流儀で、それに合わせる。

後からごはんの締切通知を足すときは、`due` の隣に同じ形の判定関数をもう 1 つ書き、ループ
から呼ぶ。今の時点で共通の枠組みを作らない。判定が 1 つしか無いうちは、抽象化する対象が
無い。

## 重複の防止

1 分ごとに走査し、通知の窓が 5 分あるため、同じ枠が 5 回続けて条件を満たす。送信済みを
集合に持ち、既にあれば飛ばす。これが今回の実装で唯一まともに考える必要のある点。

**鍵は `date|room|slot|member_id` を連結した文字列とする。`reservation_id` は使わない。**
`bath_reservations` の `id` は `INTEGER PRIMARY KEY` で `AUTOINCREMENT` が無く、SQLite は
削除された ID を再利用する。取り消しは DELETE なので、通知済みの予約が消えたあとに別の
予約が同じ ID を得ると、その人への通知が飛ばない。4 つ組は `UNIQUE (date, room, slot)` が
一意を保証しており、この事故が起きない。加えて、通知後に枠が別の人へ渡った場合も
`member_id` が変わるため、新しい人へ正しく通知される。

集合は小さな JSON ファイルへ書き出し、起動時に読み直す。systemd の `Restart=always` が
効いているため、例外で落ちると 3 秒後に再起動し、記憶を失ったまま同じ枠へ投稿し続ける
状態に入り得る。連投は運用中もっとも困る壊れ方で、防ぐ費用は読み書き数行しかない。
ファイルが読めなければ空の集合として起動する。滞在全体でも 500 件程度にしかならないため、
消し込みや日ごとのリセットは行わない。記憶を捨てる操作は、防ごうとしている重複を招く。

## メッセージ

```
<@U01ABCD2EF> あと5分で 風呂（浴槽付き） 19:00 です
```

- メンションの書式は `<@` + member ID + `>`。表示名では通知されない。
- 対応表に無い人は `あかりさん あと5分で …` と平文で出す。通知は飛ばないが、投稿自体は
  落とさない。
- 浴室の日本語名（`shower` → 風呂、`tub` → 風呂（浴槽付き））は API が返さないため、
  bot 側に対応を持つ。`src/config.js` の `ROOM_LABELS` と同じ内容を書き写す。文言が
  変わることは滞在中に起きないため、共有せず 2 箇所に置く。

## 対応表

`bot/slack-users.json` に名簿の名前をキーとして手で書く。

```json
{ "あかり": "U01ABCD2EF", "たかし": "U01GHIJ3KL" }
```

member ID は Slack のプロフィール → その他 → 「メンバー ID をコピー」で 1 人ずつ取る。
23 人なら手作業のほうが速い。`users.list` を叩いて自動生成する道もあるが、そのために
トークンとスコープを増やすことになり、しかも名簿の「あかり」と Slack の表示名は一致
しないため結局手で直す。一度きりの作業に仕組みを増やす価値が無い。

名簿の名前はデータベースで `UNIQUE` なので、名前をキーにしてよい。ただし名前を変えると
対応表が黙って壊れる。起動時に `GET /api/v1/members` を引き、名簿にあって対応表に無い
名前をログへ出す。メンションが平文へ化けるだけの故障は、これが無いと気づけない。

## 設定

| | |
| --- | --- |
| `SLACK_WEBHOOK_URL_TUB` / `_SHOWER` | 浴室ごとの投稿先。環境変数で渡す。コードにも git にも置かない |
| `SLACK_WEBHOOK_URL` | 上が無いときの共通の投稿先 |
| `API_BASE` | 既定 `http://127.0.0.1:8080` |

投稿先チャンネルは Webhook の発行時に固定される。浴室ごとに Slack のチャンネルが分かれて
いるため、Webhook も浴室ごとに持つ。1 本が 1 チャンネルに固定される仕組みである以上、
投げ分けるには本数を分けるしかない。bot 側はチャンネル名を持たず、環境変数の名前と浴室の
対応だけを知る。

判定は epoch ミリ秒の比較で行うため、プロセスのタイムゾーン設定に依存しない。systemd に
`TZ=Asia/Tokyo` を書くのはログを読みやすくするためだけ。

## 失敗したとき

- アプリが落ちていて `fetch` が例外を投げる場合は、捕まえてログを出し、次の分へ進む。
  bot が道連れで死ぬと、復旧に人手が要る。
- Slack への POST が失敗した枠は送信済みに記録しない。窓が 5 分あるため、次の分に自然と
  再試行される。専用の再送処理を書かない。
- 対応表に無い人は前述の通り平文で投稿する。

## 確かめ方

`test/notify.test.js` に `due` のテストを書く。固定した API 応答の JSON を用意し、`now`
をずらして次を確認する。

| 入力 | 期待 |
| --- | --- |
| 開始 4 分前、`taken` | 選ばれる |
| 開始 5 分ちょうど前 | 選ばれる（境界を含む） |
| 開始 6 分前 | 選ばれない |
| 開始 1 分後（過ぎている） | 選ばれない |
| `free` の枠 | 選ばれない |
| 既に送信済み | 選ばれない |

実地では、自分で直近の枠を予約して 5 分前に届くかを見る。メンションが青いリンクとして
表示されるかは目で確認する。ID を間違えても Slack はエラーを返さず、文字列のまま表示される。

投稿先チャンネルに本人が入っていないとメンションは届かない。試す前に全員を入れる。

## 後回しにしたもの

- ごはんの投票締切の通知。誰が未投票かは API から取れないため、API の拡張か SQLite の
  直読みが要る。着手する時点で設計し直す。
- 予約が成立した瞬間の投稿。起動直後に既存の予約を全て投稿しないよう、初回だけ集合へ
  詰めて黙る処理が要る。
